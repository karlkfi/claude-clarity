# A gate trains the re-check habit for its shape, not the claim's class

Blocked by [Q1003](Q1003.md). This row parks a clause for a body held
shrink-only, so it cannot land until that pass decides where the room comes
from. Q1003 is deleted and its settlement re-filed as Q1014 by an open pull
request, so this blocker re-points when that lands.

**What is already covered, and is deliberately not filed.** The session in
[Q1017](Q1017.md) also wrote a PR body saying a stacked branch carried two of
its parent's commits when it carried three. That sentence was true when written
and was falsified by a rebase onto a parent that had gained a commit — no
re-read of it catches that, because the sentence never changed. §1's *The
measurement that justifies a change is taken on the tree without the change in
it* already states the rule and the repair, re-derive every figure against the
head you are about to publish from, and carries a stronger exhibit than this
one: seven figures gone stale under one worker across five rebases, `make check`
green through every one. Nothing to add there. What is left over is the reason
the habit did not fire.

**The residue.** The same rebase could have moved a test-failure line number
quoted in the same PR body — `scan_test.go`, line 191. That one *was*
re-checked, and
had not moved. The measuring session attributes its own re-check to that repo's
citation linter, which flags a stale `path:N:text` pointer and had trained the
habit — for the shape the linter recognises. A prose count of commits is the
same class of claim, with the same expiry and the same event triggering it, and
no linter behind it, so it inherited none of the habit. That attribution is the
author's account of its own behaviour and is not independently checkable; the
two states it separates are.

**A second exhibit, from an unrelated session.** Q1014 records a citation moved
into a table cell to clear a `queue.py` false positive. A table cell is not a
`path:N:text` citation, so the linter cannot see it at any window, the line
numbers in that table were wrong within the day, and nothing marked the change
from checked-by-a-gate to checked-by-nobody. Read from that pull request's body
on 2026-09-21 and not re-derived here. Two sessions reaching the same shape
from opposite directions — one where the gate's blind spot was never entered,
one where a fix walked a claim out of the gate's sight — is what lifts this off
the first exhibit alone.

**The tell is a class of claim with a gate over part of it.** Ask which members
the gate's pattern can actually see, and treat the rest as unchecked rather than
as covered by the habit the gate built. A partial gate is worse than none for
the members outside it, because the feeling of coverage it supplies is not
scoped to the members it covers — and the boundary is a property of the
pattern, which nobody re-reads, rather than of the claim, which is what the
author has in mind.

**Ask:** whether this is a `verify-claims` clause at all. It is a rule about
where an author's verification habit comes from, which is this skill's subject,
but `gate-audit` — in `claude-skills`, not here — owns which mechanisms sit at
the wrong rung and would read this as a gate whose pattern is narrower than the
class it is trusted for. Both readings are defensible and only one is in this
repo, so the routing is a maintainer call rather than something the files
settle. If the answer is `gate-audit`, this row closes and the work is a chip in
that checkout, not a clause here — and the Q1003 block stops applying.
