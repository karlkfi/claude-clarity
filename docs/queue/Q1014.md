# Relocate the low-uptake rules and land the parked clauses in one branch

[`decisions.md`](../decisions.md) settles the route: relocation, because the
tier ladder is inert for this body — `oversize()` holds it to
`max(ceiling, baseline)` and the baseline is 110,854, so `hot`, `warm` and
`cold` all pass and reassignment changes nothing. This row is the move.

**It carries the three parked clauses too, and that is not scope creep.** The
grandfather baseline is `git merge-base origin/main HEAD`, re-read per branch,
so a shrink that merges makes main's smaller size the new limit. Driven through
`validate-skills.py`'s own `oversize()`: this move alone passes at 89,734
against a limit of 110,854; one 1,024-byte clause added off the *new* main then
fails at 90,758 against a limit of 89,734, which is the identical failure it has
today; all three fail by 3,072. Only a branch that relocates and adds passes, at
92,806 against 110,854. So a move filed on its own unsticks nothing, and Q274,
Q1010 and Q1012 land here or they do not land. Whether the three fold into one
clause is argued in Q1010 and still open.

**What moves.** The 21 rules the residency reading puts at `BLIND` or `FLAT`,
21,120 bytes of the 110,854-byte body, re-measured 2026-09-19 at `6b88023`. The
reading and its invocation are in
[`verify-claims-residency.md`](../verify-claims-residency.md); take it again
rather than quoting these bytes, because the corpus grows.

**A sibling branch takes the set to 20, deliberately.** The lane working the
small rows folds `A skip is not a defense` (310 B) into a new rule rather than
leaving it for this move, on the argument that a low-uptake rule promoted into a
high-uptake neighbourhood beats one relocated to `references/` — and that this
row files the move rather than executing it, so the collision is indefinite
rather than adjacent. Verified here against the merged tree rather than taken on
its word: of the 21 candidate leads, 20 survive as leads and exactly that one
does not. Re-derive the set after that branch lands; do not subtract by hand.

**Take the move list from the flagged run, not only the totals.** The two
readings are not nested — measured 2026-09-19, they share 20 rules, the bare run
holds 6 the flagged one does not, and the flagged one holds 1 the bare does not.
So a list built from a bare run moves a rule this reading keeps and keeps a rule
this reading moves, and the byte total it reports is right for neither.

**A displacement may not be paid out of a relocation candidate.** Measured by
the lane working the small rows while it paid its own: every unit in this body
that can be cut without losing a claim is measured low-uptake, which is this
candidate set. Its first four sentence-compression passes over high-uptake prose
returned 100, 22, 48 and 60 bytes. So an addition that displaces a candidate
spends this move's own room early and at a worse rate than moving the rule
wholesale.

**What the reading licenses.** A ranking for relocation, and not a verdict that
anything is unused. Take the candidate set as the **union** of `BLIND` and
`FLAT` and never the split: re-taken three times on one base tree inside an hour
it went 14/7, 10/11, 8/13 while the union held byte-identical. `BLIND` means no
firing anywhere in the corpus, and the corpus grows as sessions run — including
the sessions working on this file — so that boundary moves under you. Relocation
is reversible and ships the rule either way, so a ranking is enough; deletion
would need a verdict the reading cannot give, and nothing here may delete a
rule.

## The citations this move has to carry

Ten `path:N:text` citations point into `SKILL.md` from five rows. **Five point
at text the move relocates**, so those are a path change into `references/`
rather than a re-point — the line does not move down the file, it leaves it, and
`--citation-window 0` will not report that because the fragment still exists
somewhere in the repo.

**This table carries no line numbers on purpose.** An earlier revision listed
them and they were wrong within the day: a sibling branch inserting a rule moved
`A figure you derived…` from 1364 to 1365 and `Two causes that predict…` from
813 to 819, so the table contradicted the very rows it inventories. Worse, a
table cell is not a `path:N:text` citation, so `queue.py` cannot see it at any
window — putting the numbers here moved them from *checked by a gate* to
*checked by nobody*, with nothing marking the transition. The row and the rule
name are the durable address; resolve the number against the tree you are
moving, which is the same fragment-over-number rule the drifted citations below
already demonstrate.

is no "the candidates are all above the citations" shortcut — an earlier draft
of this row claimed one and it was false.

**Why it did not land with the decision.** A concurrent lane was editing this
body and repointing three of the rows above from the other side, and a citation
two open branches both move resolves to a number wrong whichever lands second.
Re-read that state before starting; it was true on 2026-09-19 and expires.

**What would reverse it:** a reading that separates consulted from applied. The
present one cannot see a rule applied in the reader's own words, so it ranks by
what reaches a session's output rather than by what a reader needed. If Claude
Code ever reports which part of a resident body a turn attended to, re-derive
the candidate set before anything moves. Or a grandfather keyed to a recorded
high-water mark rather than a re-read of main, which would make room bankable
and let this row shed the three clauses again.
