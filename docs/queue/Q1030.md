# A residency verdict read off one reader session looks like a ranking

`verdict()` compares a rule's rate after the load with its rate before, and
nothing in it asks how many sessions those rates came from. With one reader
session and a two-block `PRE` window, any rule that fires once after the load
reads `RAN`, and the `# verdicts:` line reports it in the same form as a reading
over eighty sessions.

**Measured 2026-11-01** on the branch that taught the probe to read reference
files (`d06feba`), with `--repo claude-clarity --repo claude-skills`:
`scripts/rule-residency.py skills/verify-claims/references/timing-and-concurrency.md`
prints `# use:sessions: 1`, `# use:pre:action:blocks: 2` and
`# verdicts: RAN=12  SAID=2  FLAT=0  BLIND=1`. That one session read the file on
2026-08-16 without invoking the skill. The `use:sessions` line is on stderr, so
the sample size is visible, but only to a reader who looks for it among the
other `reach` counters.

Reference files make this the common case rather than an edge one. On the same
date, none of the 98 reader sessions invoking `verify-claims` had read any of
its eleven reference files whole, so every reading of one is taken over
sessions that read the file without the skill, and the reader arm holds one
such session or none per file.

**What to build:** a floor on reader sessions below which the run prints the
table without verdicts, or with a verdict that says the sample is too small,
and says so on the `# verdicts:` line. No reading on record settles the exact
floor. The ones this script has published held 85 to 89 reader sessions, so
any floor that refuses one session and accepts those is defensible as a start,
and the docstring should say that the number was chosen rather than measured.
Add a fixture with one reader session and assert the guard fires.
