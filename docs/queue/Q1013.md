# Gate the two residency lines that say which reading you are holding

`scripts/rule-residency.py` prints a `# authoring repos` line on every run and
writes `verdict` and `repos` keys into `--json`, and nothing checks any of them.
A future edit can drop one and `make check` stays green. The row was filed
asking whether a suite built to avoid a corpus should take one to cover them.

**Measured 2026-09-19 at `6b88023`: it does not need one, and the check costs
54 ms.** A synthetic transcript tree — two project directories, one `.jsonl`
each, four records apiece — exercises the shipped path end to end with
`PROJECTS` reassigned, so nothing reads `~/.claude/projects`. An independent
review reproduced it at 55 ms from its own arm.

**Assert the discrimination, not the wording.** The review of the original PR
declined a `--help` string check as a gate that fails on rewording, and that
objection kills the obvious form of this one too — `startswith("# authoring
repos:")` reddens when someone renames the prefix. The form to build runs the
same synthetic corpus twice under two different `--repo` values and requires
the two readings to differ, each naming its own segregation and recording its
own `repos`. Measured: two different first lines, two different `repos` arrays,
two different verdict tables from one fixture.

**Two probe shapes were measured, and their mutant tables differ — build the
second and do not carry the first's numbers over.** This row's first draft gave
a single table without saying which shape produced it, and the review caught
it. Three mutants of the instrument, each confirmed landed by reading the file
back rather than by the writing command's status. The fourth is the regression that actually produced the reading confusion above, and the two-reading probe reddens every assertion it has on it:

| mutant | prefix-asserting probe (6 assertions) | two-reading probe (5 assertions) |
|---|---|---|
| drop the `# authoring repos` print | 2 red, 6 ran | 2 red, 5 ran |
| drop `"repos": repo_names` | 1 red, 6 ran | **aborts, 0 ran** |
| drop the `r["verdict"] = ...` loop | 1 red, 6 ran | **aborts, 0 ran** |
| ignore `--repo`, always `[default_repo()]` | 3 red, 6 ran | **5 red, 5 ran** |

Three things an implementing session needs from that table. **Read the `--json`
keys defensively** — the two-reading probe indexed `doc["repos"]` and
`r["verdict"]` and died on `KeyError` before any assertion ran, so the mutant
was reported by exit status and not by a named assertion; `.get` and `in` keep
the failure legible, which is what the prefix probe did and why it ran all six
every time. **A "a repos line is present" assertion that only requires some
stderr line starting with `#` is a vacuous positive** — the next line is
`# auth:post:action:blocks: N`, so it stays green with the print deleted. The
review found this independently; it is the shape to avoid. And **the
whole-stderr comparison reddening above is fixture-dependent**. Assert that
each first line names its own segregation; do not rest on whole-stderr
inequality.

**Pick the fixture last, because its symmetry decides which assertions can
fail — in both directions.** Two properties pull against each other. Sessions
with matching block counts make the whole-stderr comparison sharp, since
deleting the print leaves the two runs byte-identical and the assertion
reddens; sessions that differ in which rule fires keep the verdict tables
distinguishable. The fixture measured here has both — its two runs differ on
stderr only in the repos line, and their verdict tables are `[RAN, FLAT]`
against `[FLAT, RAN]`. Giving the sessions different block counts buys the
second at the cost of the first: the stderr assertion then passes with the
print deleted. The review of this PR reports hitting that inversion from the
other side, its verdict-table assertion failing on the intact tree until it
made its sessions asymmetric — its measurement, not re-derived here. Neither
arm shows this alone, which is why it is written down.

**The line earned its keep within a day of shipping, which is the case for
gating it.** A reading taken 2026-09-19 at `6b88023` returned 26 low-uptake
rules and 26,639 bytes where `docs/verify-claims-residency.md` records 21 and
20.6 kB, and the swing went unexplained. Re-taken the same morning at the same
commit: the flagged invocation the doc publishes returns 85 reader sessions, 11
authoring ones, `RAN=53 SAID=14 FLAT=7 BLIND=14`, and 21 rules over 21,120
bytes — the doc's table, a day and seven reader sessions later. The bare run at
the same minute returns 92 reader sessions, 4 authoring, `RAN=47 SAID=15
FLAT=12 BLIND=14`, and 26 rules over 26,639 bytes. The 7-session gap is the
`claude-skills` authoring sessions the second `--repo` segregates, which is what
the doc predicts and warns about in the paragraph above its table. So the
instrument is stable and the reading was the bare one; the `# authoring repos`
line printed `claude-clarity` alone and was the only thing in the output that
said so. Nothing gates the one line that made the difference legible.

**The two candidate sets are not nested, so a reader cannot recover the
published one by subtraction.** Verified here from both runs' `--json`: they
share 20 rules, the bare set has 6 the flagged set does not, and the flagged set
has one the bare set does not — `Provenance is a claim, and one of the cheapest
to settle` is FLAT under the flagged reading and SAID under the bare one. The
bare run substitutes members rather than merely adding them. Raised by the
Q1003 lane and re-derived here rather than repeated.

**A second defect in the same file, folded in here rather than filed
separately** — the repair is two lines of fixture in the file this row already
edits, and a separate row would contend with this one on it. The harness check
named *mid-paragraph emphasis is not counted as a rule* passes with the
paragraph-opening guard deleted: 8 ok, 0 FAIL. The fixture's emphasis sits
mid-line, where `re.match(r"^\*\*...")` rejects it on its own, so the guard the
check is named for is never exercised. A fixture wrapping a bold span to the
**start** of a line separates them — `rules: 2` intact, `rules: 3` with the
guard gone. The harness's own comment above that fixture already says the span
"lands at the start of a line only because the prose wrapped there", which the
shipped fixture does not do — so the repair restores the fixture to its own
documented intent rather than adding a case. The shipped guard is correct; only
the control is vacuous, so this is a regression risk rather than a wrong number
in the published table.

**What the implementing session also owes.** The harness header says *nothing
here touches `~/.claude/projects`*, and a synthetic corpus reads as
contradicting it — amend that comment to distinguish a fabricated tree from
machine state, or the next session deletes the new arm for violating the file's
own stated scope. Add a `docs/decisions.md` entry recording that a corpus-free
suite may fabricate a corpus, since the alternative is re-litigating it. The
repo's existing bar for building a check — certain and mechanically repairable,
from the entry refusing three linters — is met: a key is present or it is not,
and the repair is restoring the line.

**What would reverse it:** the probe reassigns `rr.PROJECTS`, a module global,
so a refactor making the projects root an argument or a class attribute breaks
the seam and the arm has to follow it. That is the coupling to watch; it is one
name, and the harness already imports the module by path for its verdict arm.
