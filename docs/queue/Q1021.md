# A checker was refused as a gate and never scored as an instrument

[`decisions.md`](../decisions.md) refuses a linter for `semantic-remediation`,
`claim-provenance` and `tech-docs-layers`, re-tested 2026-09-18, on one pair of
criteria: a finding has to be **certain** and **mechanically repairable**, or
the script emits a warning a human must adjudicate and the warning goes unread.

A pass handed here on 2026-09-24 used the two shipped linters for a second job
that pair does not cover. Run over the text sessions actually authored,
`deslop-lint.py` puts 20 of 224 unfired README units at or above 7.0 hits per
100 words, and `readability-lint.py` finds 32 of 190 carrying a term used and
never expanded. Those were the only figures in the whole pass bearing on
whether a skill *should* have fired. The other eight can be scored only against
a predicate paraphrasing their own description, which measures the paraphrase.

**An instrument has no actor to interrupt.** It reports an aggregate over a
corpus, so the unread-warning failure that kills a gate costs it nothing, and
"mechanically repairable" drops out of the criteria entirely. What replaces it
is narrower and harder: the script's finding has to *correlate* with the
occasion the skill exists for, well enough that a rate computed from it decides
something.

## What to settle

**Ask:** whether an instrument-only checker is a thing this repo ships at all.
It is a script in a skill's `scripts/` directory that no gate runs and whose
output no session reads, which is a shape the repo does not currently have, and
the cost lands on every future reader of that directory.

Then, if yes, which of the five skills carrying no ruling can hold one —
`brevity`, `code-restraint`, `substantiate`, `verify-claims`,
`rendered-page-review`. Judge each against the instrument criteria above rather
than the gate pair, and record the ones that fail either way.

`code-restraint` is the tempting candidate and worth naming for the same reason
`tech-docs-layers` was: comment-to-code ratio against the host file is exactly
computable, and whether a given ratio is *wrong* is a norm rather than a rule,
which is the objection that sank the front-matter-key check. As an instrument
that may not matter — an aggregate over many diffs can tolerate per-diff
ambiguity a warning cannot — and that is the claim to test rather than assume.

## What this does not reopen

The three refusals stand on their own reasoning, and one of them survives the
change of criteria unaltered. `claim-provenance`'s finding is the gap between a
sentence's register and its provenance. A script reads the register and never
the provenance, so it computes one term of a subtraction. That marks a measured
number and an invented one identically, which is as fatal to a count as to a
warning.

## Cost the build before agreeing to it

The two existing linters each ship a test harness and a catalog-sync test, so
the unit of work is larger than one script. Measure what the two cost before
sizing a third:

```bash
wc -l skills/deslop/scripts/*.py skills/deslop/scripts/*.sh
wc -l skills/readability/scripts/*.py skills/readability/scripts/*.sh
```

Whether an instrument-only checker needs the same harness is part of the Ask —
nothing gates its output, so a sync test against prose it does not enforce may
be the wrong shape.

## Provenance

The counts are handed over from a pass whose instruments live in a private repo
and are not re-derivable here. Both carry floors the pass stated: the linters
see vocabulary and sentence mechanics and cannot see a claim with no source, so
20 of 224 and 32 of 190 are lower bounds. And `readability-lint.py` covers one
of that skill's three rules rather than its subject.
