# Hooks belong here, and nothing in the repo installs one yet

Naming a skill in a `CLAUDE.md` raises its trigger rate and then saturates well
short of the occasion. A hook is the only rung that fires at the moment the
occasion occurs, and the goal it serves here is this repo's goal — getting the
prose passes to run when they apply — rather than `claude-bouncer`'s, which is
denying an action that is wrong on its own terms. Same mechanism, different
job, so the hook ships with the skills it serves.

Measured 2026-09-14 over 2,117 local session transcripts, one workstation.
Occasion counts, not invocation counts:

| skill | occasion | fired |
|---|---|---|
| `code-restraint` | edited a source file and ran `git commit` | 13/531 (2.4%) |
| `code-restraint` | same, 5 or more source files | 2/138 (1.4%) |
| `rendered-page-review` | edited a page `github-actions-gateway` publishes | 0/162 |
| `tech-docs-layers` | edited 8 or more `docs/*.md` files | 2/65 |

Three readings behind the design. The rate **falls** as the diff grows, so the
sessions least likely to reach for a pass are the ones with most to gain.
**16 of `code-restraint`'s 29 firing sessions wrote no code at all** — the pass
fires when reviewing a diff is the session's purpose, not when it is incidental
to some other task, which is the same shape `rendered-page-review` shows. And
naming does work: `code-restraint` ran 1.3% before the global `CLAUDE.md` named
it and 5.4% after, a four-fold move to a number still far short of the
occasion.

`code-restraint` is the first rule to write, because its stated occasion is
literally "before committing a code diff" and a `PreToolUse` on `git commit`
matches it exactly. `rendered-page-review` is a worse fit for a hook: its
catches are threshold-shaped and belong in a render gate, which is why that
half went to the repo that publishes pages rather than here.

Follow `hook-attribution` for anything the hook emits, and settle the verdict
with `hook-verdict` rather than assuming a nudge must be advisory — its routing
test asks whether the fix can be written into the reason, and here it can:
*run the pass, then commit*. A deny reaches the model and gets applied; an
`ask` reaches the human and teaches the session nothing.

**Ask (answered):** the repo gains a plugin manifest beside `install.sh`, so
hooks reach a machine through the plugin system the way `claude-bouncer`,
`pr-sentinel` and `spill-guard` already do. `install.sh` is untouched and goes
on linking skills and styles, so [decisions.md](../decisions.md)'s rule that the
installer writes no settings survives intact rather than being reversed — the
repo is both a clone-and-script bundle and a marketplace, and neither path
hand-edits a settings file.

That rule was raised because it looked like a conflict and is not one. The
entry argues from output styles being mutually exclusive: activating one
replaces whichever style the machine runs, so the choice is the machine's. A
hook displaces nothing and inherits no part of that argument, which is why the
question was open; the answer keeps the rule anyway by routing around it.

**This depends on [Q1001](Q1001.md), and answers half of it.** That row asks
whether to publish and, if so, as a plugin or as a clone. The answer above
settles the second half and leaves the first untouched, because it was made for
the hook rather than for distribution.

**Check one capability before planning against it.** Writing the manifest and
the hook is not blocked by anything. *Installing* them here might be: all four
marketplaces on this machine are `source: github`
(`~/.claude/plugins/known_marketplaces.json`, read 2026-09-14), and whether a
local clone with no remote can serve as a marketplace is unverified — no
example of one exists on this machine to read. If it cannot, this row is
blocked on Q1001 rather than merely downstream of it, and the hook cannot be
used here until publishing is decided.

Two consequences to build against. Plugin auto-update does not work on this
machine — `autoUpdate: true` is persisted and nothing consumes it — so an
installed copy goes stale silently and the README has to say how to update it.
And a second install path needs documenting without implying the skills now
require the plugin: any one skill still runs alone, and somebody who wants the
prose passes and no hooks should not have to take the marketplace.
