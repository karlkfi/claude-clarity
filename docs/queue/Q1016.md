# The residency verdict moves because the reading is being discussed

**Event:** `rule-residency.py` can take a reading of a skill's `references/`
files, where the `verify-claims` rules now live (filed as Q1029 on the branch
of PR #33, unmerged when this was written). Until then nothing will take the
reading this row would change, so nothing is waiting on it.

`` `scripts/rule-residency.py:303:    if row["corpus"] == 0:` `` is the whole
definition of `BLIND`, and corpus is
`` `scripts/rule-residency.py:30:    corpus  every firing anywhere, PRE and POST and authoring sessions alike.` ``.
So a rule leaves `BLIND` the first time its vocabulary appears anywhere in the
transcripts, including in the sessions deciding whether to relocate it. The
instrument takes a rule out of the relocation candidate set because someone is
discussing relocating it.

## Which remedy

**Ask (answered):** the repo had already chosen, in a decisions entry this row
never cited. The
entry *What the residency reading licenses is a ranking, not a verdict* in
[decisions.md](../decisions.md) says to quote the union of `BLIND` and `FLAT`
and never the split. It landed as `4f4ca48` on 2026-09-19 at 09:49, on a branch
parallel to the commit filing this row (`b8a84e3`, 11:11). `git merge-base
--is-ancestor` says the filing commit does not contain it, which is how the row
came to ask a question that was already answered. The relocation the reading
served used the union and shipped on 2026-10-04 (Q1014).

That settles the three remedies this row offered:

- **Report the union only, for anything a decision quotes.** This is the
  decisions entry, so it is already policy. It costs the `BLIND`/`FLAT`
  distinction, and the same entry says nothing consumes that distinction:
  relocation needs only a ranking, and deletion "is not on the table at any
  ranking".
- **Exclude the deciding sessions from `corpus`.** Rejected. It would hold
  still a split no decision reads, and it needs a rule for which sessions count
  as deciding, which has no clean answer: a session that reviews a rule may
  also apply it.
- **Stamp every reading.** Adopted as the build, because it addresses the one
  failure on record that the quoting rule cannot. A reading in this row's
  history was taken with the worktree on the Q146 stack (body blob `c518b27`)
  and nothing in its output named the blob. It returned the same five verdict
  figures as a real reading, reached a filed row and survived one review.

Every input to this choice is source or a decisions entry, not a count, so the
wrapped-lead fix (Q1028, in flight as PR #33), which changes what counts as a
rule, does not move it. This pass took no fresh reading.

## What to build on revive

Built against the script as it stands after Q1028 and Q1013 (PR #34, which
gates the `# authoring repos` line). All three rows edit the same script and
`scripts/test-rule-residency.sh`, so this one goes last.

1. On stderr, beside `# verdicts:`, print the stamp: the body's blob id from
   `git hash-object`, the corpus record count, and the date. Print the union as
   its own figure, rules and exact bytes, so nobody sums it by hand from the
   rounded `kB` column. Add `blob` and `union` to `--json`.
2. Keep the four-way split in the per-rule table. `BLIND`'s docstring is what
   stops a blind rule being reported as unused, and
   `` `scripts/test-rule-residency.sh:109:check silent BLIND "a rule that never fires anywhere reads BLIND, not unused"` ``
   asserts it on its own.
3. Assert the stamp line in the two-reading probe Q1013 adds: the two runs over
   the same fixture print the same blob, and a run over a different body prints
   a different one.
4. Correct the ratchet wording (item below), in the decisions entry and in
   [verify-claims-residency.md](../verify-claims-residency.md).

**The ratchet is not permanent on this machine.** Both docs say a rule leaves
`BLIND` and does not come back. That holds only while the transcript store
grows. `~/.claude/settings.json` sets `"cleanupPeriodDays": 365`, which the
Claude Code settings index describes as the number of days it "keeps
transcripts before deleting them". Measured 2026-11-01: 2,790 `.jsonl` files
under `~/.claude/projects/`, the oldest modified 2026-07-28, 95.9 days ago. So
nothing has been pruned yet, and from about 2027-07-28 the corpus can shrink
and a rule can return to `BLIND`. This was the retention question this row left
open. Not re-measured: the 365 is this machine's setting, and anyone running
the probe elsewhere has their own.

**Who it is for:** a session taking a residency reading to decide what to move
out of a skill body. Today's `verify-claims` body holds 4 rules on the current
build, so that session cannot exist until the probe reads reference files.
**If it is never built:** a reading taken against the wrong tree will again
produce plausible numbers that name no blob. One of the six readings this row
recorded in September was of the wrong blob. **Rate:** `rule-residency.py` was invoked in 84 Bash calls
in September, 12 in October and 24 on 2026-11-01 alone. These are counts of
transcript `tool_use` blocks, which also include test and `--help` runs, and
today's are mostly stream A working Q1028. The cost is steady, neither accruing
nor perishable. **Rank on revive:** after Q1029's build, since it is what
brings the readings back. `b1d` holds until then.
