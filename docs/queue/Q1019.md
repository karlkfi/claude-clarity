## What is not covered

**A comparison you validated in one state, where the claim spans several states
that differ in their reference.** The existing family asks what question the
instrument answered. This asks in which world it answered it, and a probe that
is correct in the state you ran it in returns a clean result there and is silent
about every other one. Re-running it more carefully cannot reach them.

Two instances, both from one parallel-dispatch run in `karlkfi/claude-spill-guard`
on 2026-09-21, both the measuring session's and **not re-derived here** — that
repo is not this one and the run is over.

A citation collision was solved by computing the correct line number in the
fully merged tree. Exact, and the wrong state: in a tree where only one of the
pull requests had landed, that PR's own citation drifted 18 lines against a
10-line tolerance, so the proposal would have reddened its CI before anything
merged. And `git merge-tree --write-tree origin/main <branch>` run against each
of three branches returned three clean results, all correct, for a set that
still conflicted — the first merge is what moves the line the second one cites,
so pairwise-against-trunk is structurally blind to a chained set.

**The tell:** the change has to survive more than one tree, and each tree is a
different left operand. Ask which states the thing must hold in, not whether the
one you measured was measured correctly. Where the states are a merge sequence,
build them in order.

**This store already holds the sharper exhibits, in-repo and reproducible**, and
a session writing the clause should lead with them rather than with the
handed-over pair above. [Q1016](Q1016.md) records a residency reading taken with
the worktree on a branch in the Q146 stack, so it read blob `c518b27` and not
the `584d604` it was offered as a control for; it returned the same five verdict
figures and reached a filed row. The same row records a citation audit run
against the Q146 branch head rather than the PR's base, returning three
confident misses where all four citations resolve against `main`. Both are the
same shape as the two above and neither is filed as a rule.

## The entry condition, and the half that leaves this repo

In the manufactured-finding case the wrong operand **arrived in a message**:
the worker was told "#179's ancestry reaches `b9d91ae7`", which was true, and
used it as a diff base, where the fact needed was the merge-base `dbd19eb4`.
Every instance the body carries has the reader choosing their own wrong ref. So
the increment on that family is one clause of entry condition handing into it —
re-measure a handed-over reference before it becomes an operand, because the
sender cannot know what you will do with it — and not a restatement of the
mechanism.

**The sending half is not this skill's.** *Name the merge-base, say that is what
it is, and measure it at the moment of sending* is a rule about what a handover
message carries, which `session-worker` and `session-orchestrator` own in
`karlkfi/claude-skills`. Chipped there 2026-09-21; that row and this one
cross-reference rather than co-locate, because the two halves are performed by
different roles. The counter-argument is the pairing's own: a sender who forgets
is caught by the receiver and a receiver who forgets by the sender, so splitting
them across repos means neither file states the pair. Both skills load
`verify-claims`, so co-locating both halves here would work; it is a maintainer
call and the chip records it as open.
